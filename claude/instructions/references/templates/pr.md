# PR 템플릿

GitHub PR 작성·등록에 적용한다. GitHub 작업은 `gh` CLI를 사용한다.

## 등록 절차

PR 생성 요청 시 다음 순서를 따른다.

1. **base 브랜치 확정**: 사용자가 지정하지 않으면 분기점으로 감지한다 -
   `git fetch origin` 후 merge-base로 origin의 기본 브랜치와 `origin/release/*` 중
   현재 브랜치가 어디서 분기했는지 확인. `release/*`에서 분기했으면 그 브랜치,
   아니면 기본 브랜치. 감지 결과를 등록 전에 사용자에게 알리고,
   base 미확정 상태로 등록하지 않는다.
2. **원격 상태 확인**: 미푸시 커밋이 있으면 개수를 보고하고,
   하드 룰 5에 따라 확인 후 푸시한다. 푸시 실패 시 중단하고 원인을 보고한다.
3. **변경 분석**: `git log`, `git diff --stat` (base..HEAD)로 커밋과 변경 파일을
   파악하고, 실제 파일을 읽어 확인한 사실만 본문에 쓴다. 변경이 없으면 중단한다.
4. **로컬 검증**: 저장소에 정의된 명령으로 lint, 변경 부분에 대한 단위 테스트,
   빌드를 실행한다.
   - 검증 범위는 변경 범위로 한정한다. 모노레포면 변경된 패키지/앱만 실행한다
     (`nx affected`, `turbo --filter`, `pnpm --filter` 등 저장소가 쓰는 방식).
   - 명령은 저장소 설정(package.json scripts, 프로젝트 CLAUDE.md, Makefile 등)에서
     찾고, 정의되지 않은 항목은 스킵하되 스킵 사실을 보고한다.
   - 하나라도 실패하면 등록을 중단하고 실패 내용을 보고한다.
     사용자가 명시적으로 스킵을 지시한 경우에만 생략할 수 있다.
5. **본문 작성**: 아래 골격·작성 규칙과 writing-style.md의 외부 등록 절차
   (로컬 md 초안 → plannotator 검토 → 사용자 컨펌)를 따른다.
6. **등록**: 항상 draft로 생성한다 (`gh pr create --draft`). 본문은 실제 개행이 있는
   multiline으로 전달한다(`--body-file` 권장). 등록 직전 확인은 하드 룰 5를 따르고,
   등록 후 PR 번호와 URL을 보고한다.

## 제목

영어, `<type>: <description>` 형식 (커밋 타입 목록은 CLAUDE.md Git 작업 규칙과 동일).

## 골격

필수 섹션은 Background와 Implementation task 둘뿐이다.
나머지는 각 섹션의 포함 조건을 충족할 때만 넣고, 아니면 섹션 자체를 생략한다.
확신이 없으면 생략한다.

```markdown
### Background

{변경이 필요한 이유. 1-3 불릿}

### Implementation task

{대표 변경사항. 리뷰어가 파악해야 할 변경 단위}

### Screenshot

{UI/시각 변경이 있을 때만}

### Focus it

{리뷰어가 건너뛰면 안 되는 항목이 있을 때만}

### How to test

{추가 환경 설정이나 시나리오 안내가 필요할 때만}

### To do

{확정된 후속 작업이 있을 때만}

## Reference

{관련 이슈·PR·티켓·문서 링크가 있을 때만}
```

## 섹션별 규칙

### Background

- 전략적 동기를 먼저 쓴다: 왜 필요한지, 기존 코드베이스 컨벤션과 어떻게 정합하는지.
- 부수 효과(리스크 감소, 일관성 확보)는 한 줄로 뒤에 붙인다.
- 기계적 증상이나 결함 서술로 시작하지 않는다.

금지: "기존 워크플로우는 env 설정 오류 시 예외가 발생하는 문제가 있었습니다."
권장: "다른 워크플로우가 이미 octokit을 사용하는 방식과 일치시키기 위해 gh CLI 의존성을 제거합니다. 부수적으로 CLI 인증 오류에 의한 간헐적 실패도 함께 해소됩니다."

### Implementation task

- 대표 변경만 쓴다. 파일 전수 나열 금지, diff로 자명한 내용 재서술 금지.
- 구현 스택(라이브러리명, 액션명, 권한 스코프, 표준 보안 기법)은 쓰지 않는다.
  본문은 리뷰어가 관심 있는 동작·능력을 설명하고, 방법은 diff가 설명한다.
- "시도 → 실패 → 대체" 서사는 한 줄로 압축한다 (`beforeSendSpan` 방식 비효과적 → `ignoreSpans`로 교체).
- 인과 관계가 있는 변경은 하위 불릿으로 묶는다. 상위 = 무엇이 바뀌었나,
  하위 = 함께 봐야 할 결과·부수효과. 독립적인 변경은 중첩하지 않고 상위 불릿으로 나열한다.

  ```markdown
  - `gh pr list` → `github-script` octokit으로 교체합니다
    - PR이 없을 때 동일 방식으로 실패합니다 (동작 유지)
    - `pr_number`가 step output으로 하위 스텝에 전달됩니다
  ```

- 파일 경로는 이해에 필수일 때만 쓴다: 동일 변경이 두 모듈에 적용되어 구분이 필요하거나,
  경로 자체가 리뷰 포인트인 경우(설정, 환경별 파일). 설명만으로 충분하면 생략한다.
- 섹션 내 순번 헤딩(`#### 1. ...`) 금지. 목적 중심 헤딩만 쓴다.

### Screenshot

- 미디어로 보여줄 수 있는 변경 + 자료 있음 → 스캐폴드 작성.
- 미디어로 보여줄 수 있는 변경 + 자료 없음 → `N/A (no UI changes)` placeholder만 남긴다.
- 시각과 무관한 변경(백엔드, CI, 설정, 인프라) → 섹션 자체를 생략한다.
- 이미지는 HTML `<img>`로 폭을 지정한다: 세로형(모바일) `width="280"`, 가로형(데스크톱) `width="680"`.
- 케이스가 여럿(Before·After 등)이면 표로 만들고 `src=""`를 비워 사용자가 채우게 한다.
- 콘솔 로그로 검증되는 변경은 코드블록이나 `<details>`로 실제 로그를 인라인 첨부한다.
- 스캐폴드를 만들면 어떤 스크린샷·영상·로그가 리뷰에 도움이 되는지 채팅으로 알린다.

### Focus it

- 포함 조건(하나라도 해당할 때만): 보안 영향, breaking change,
  팀 판단이 필요한 정책·아키텍처 결정, 코드만 읽어서는 놓치기 쉬운 엣지 케이스·부작용.
- "복잡하니 꼼꼼히 봐주세요" 류 일반 리뷰 요청, diff로 자명한 변경,
  루틴한 보안 위생(최소 권한 등)은 쓰지 않는다. 쓸 것이 없으면 섹션을 생략한다.
- 각 불릿은 (무엇을 / 왜 봐야 하는지) 한 줄. 판단 요청은 질문형으로 쓴다
  ("~를 사람 개입 없이 자동 종료해도 괜찮은지").

### How to test

- 포함 조건(둘 중 하나만): 표준 개발 환경을 넘는 추가 설정(env, seed, feature flag,
  외부 서비스 연결)이 필요하거나, 자동화 테스트가 특정 시나리오만 커버해 재현 안내가 필요한 경우.
- "앱 실행 후 확인", "일반 단위 테스트 실행" 수준이면 생략한다.
- 워크플로 입력·모드를 되풀이하는 단계 나열도 생략한다. 리뷰어가 이미 아는 내용이다.

### To do

- 티켓이나 확정된 다음 PR이 있는 후속 작업만 쓴다.
- 추측성 개선("추후 개선 예정", "적용하면 좋을 것 같습니다")은 쓰지 않는다.
  현재 PR이 미완성이라는 인상만 남긴다.

### Reference

- 관련 이슈·PR·티켓·문서 링크가 있을 때만 넣는다.
- 관련 티켓이 있으면 제목에 티켓 번호가 있어도 링크를 넣는다.

## 문체와 공통 규칙

- 본문 산문은 한국어 합니다체(`~합니다`, `~됩니다`). 불릿을 포함한 모든 산문에 적용하고,
  `~다`, `~한다`를 쓰지 않는다.
- 목표·의도는 의지형으로 쓴다: "~를 해소하고자 합니다", "리뷰 후 1차 병합하려고 합니다".
- 영어 병기 괄호를 붙이지 않는다. 한국어 용어로 충분하면 한국어만 쓴다
  ("중간 병합(intermediate merge)" → "1차 병합"). 확립된 용어로 한국어 대응어가 없으면 예외.
- 근거 기반 서술: 추측성 "개선/강화" 대신 구체적 동작 변화를 쓴다.
- AI 생성 attribution 푸터를 붙이지 않는다.

## 초안 자기 점검 (plannotator 검토 전)

- [ ] Background가 전략적 동기로 시작하는가 (기계적 증상 아님)
- [ ] 모든 산문이 합니다체인가 (불릿 포함)
- [ ] 본문에 구현 스택이 없는가
- [ ] em/en 대시가 없고, 영어 병기 괄호가 없는가
- [ ] 시각과 무관한 변경에서 Screenshot 섹션을 통째로 뺐는가
- [ ] Focus it / How to test / To do가 포함 조건 없이 들어가 있지 않은가

점검에서 걸리면 사용자에게 묻지 말고 바로 고친 뒤 plannotator 검토로 넘어간다.
