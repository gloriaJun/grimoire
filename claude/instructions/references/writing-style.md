# 한국어 글쓰기 지침

사용자의 글쓰기 스타일을 재현하기 위한 규칙. 모든 한국어 산문 산출물에 적용한다.
"문서 포맷" 섹션은 문서 산출물(가이드, 위키, README, 초안, 기술 문서)에만 적용한다.
내부 설정 파일(CLAUDE.md, SKILL.md, settings.json 등)에는 적용하지 않는다.

## 문장

- 한 문장에 하나의 내용만 담는다. 산문 문장은 60자 이내로 쓴다.
- 설명·지침 산문은 단정형("~한다/~하지 않는다")으로 쓴다. 같은 "~다" 어미를 4회 연속하지 않는다.
- 불릿과 표 셀은 명사형으로 끝낸다("검토 완료", "링크 추가"). 서술어를 붙이지 않는다.
- 확신하는 내용은 단정한다. "~할 수 있을 것으로 보인다" 같은 헤징을 쓰지 않는다.
  검증하지 않은 내용에만 "미확인"을 붙인다.

## 어휘·표기

- 번역투 금지: "X에 대해 논의"가 아니라 "X를 논의". "~를 통해"는 "~로".
  이중피동("~되어진다") 금지.
- em 대시(—)와 en 대시(–)를 절대 쓰지 않는다. 연결은 하이픈(-), 콜론, 괄호로 한다.
- 압축 나열은 가운뎃점(·), 변환·흐름은 화살표(→)로 쓴다.
- 식별자·명령·파일 경로는 백틱으로 감싼다. 기술 용어는 영어 그대로 둔다.
- 어려운 전문용어는 쉬운 표현으로 바꾸고, 유지하는 전문용어는 첫 사용 시 한 줄 설명을 붙인다.
- 이모지를 쓰지 않는다. 볼드는 문서당 2~3회 이하로 제한한다.
- 문두 접속사(또한/따라서/즉)는 문서당 4회 이하. 내용 흐름으로 연결한다.

## 구조

- 결론이나 핵심을 첫 1~2줄에 쓴다. "이 문서에서는 ~를 설명합니다" 류 도입을 쓰지 않는다.
- 메타 서술과 자기 언급은 삭제한다.
- 헤딩은 명사형으로, 순번 접두사 없이 쓴다("## 배경", "## 1. 배경" 아님).
- 구분선(---)을 섹션 구분에 쓰지 않는다. 구조는 헤딩으로만 나눈다.
  (표의 구분 행 `|---|---|`은 마크다운 문법이므로 예외.)
- 비교와 열거는 파이프 테이블로, 절차 흐름은 mermaid flowchart로 표현한다.
- 규칙이나 기준을 쓸 때는 수치 임계값을 붙인다("3개 이상", "4회 연속").

## 작성 워크플로

- 산출물 언어는 별도 요청이 없으면 한글이 기본이다.
- 최종 산출물이 영문이어도 한글로 먼저 작성한다.
  사용자가 한글판을 최종 컨펌한 뒤에 영문으로 번역한다.
- 로컬 md 초안의 검토·수정은 plannotator로 진행한다:
  `plannotator annotate <file.md>` 실행 → 피드백 반영 → 재실행을 Approve까지 반복.
- 외부 등록 글(Confluence, GitHub issue/PR 본문 등)의 절차:
  1. 현재 작업 디렉토리에 md 파일로 초안 작성
  2. plannotator로 검토, 사용자 최종 컨펌
  3. 대상 플랫폼의 양식에 맞춰 등록 (등록 전 확인은 CLAUDE.md 하드 룰 5를 따른다)
  4. 사용자가 등록 결과를 확인한 뒤 로컬 md 파일 삭제
- 아래 유형의 산출물은 해당 템플릿을 Read로 로드해 골격과 규칙을 따른다.
  기준 경로: `~/.claude/instructions/references/templates/`

  | 산출물 유형 | 템플릿 |
  |---|---|
  | PR 제목·본문 | `pr.md` |
  | 절차 안내 (하우투, 온보딩, 마이그레이션) | `guide.md` |
  | 개발 가이드 (CONTRIBUTING, 반복 참조 규칙·명령 모음) | `dev-guide.md` |
  | 실행 계획 (구현·작업 계획) | `plan.md` |
  | 제안·검토 (기술 선택, 설계 검토, 의견서) | `proposal.md` |
  | README (프로젝트 소개·사용법) | `readme.md` |
  | 트러블슈팅 기록 (회고, 이슈 정리, devlog 해결 항목) | `troubleshooting.md` |

## 문서 포맷 (문서 산출물 전용)

### 목차 (TOC)

- `##` 섹션이 3개 이상일 때만 포함한다. 2개 이하면 생략한다.
- 위치: 문서 제목 바로 아래 (도입 문단보다 앞).
- 형식: 앵커 링크가 있는 불릿 리스트.

### 완료/해결된 내용의 기록

끝난 작업이나 해결된 이슈는 미래의 독자에게 필요한 것만 남긴다.
전체 과정은 PR, 커밋, 티켓에 이미 있으므로 재문서화하지 않는다.

- 유지: 근본 원인(1줄), 수정/결과(1줄), 재사용 가능한 교훈(1줄), 참조 링크(PR/커밋/티켓).
- 삭제: 호출 체인 추적, 로그 덤프, 기각된 대안 비교, 단계별 검증 로그.
- 상세 내용은 미해결/후속 작업에만 허용된다.
- TL;DR이 이미 해결 내용을 요약하면 별도의 상세 "해결된 이슈" 섹션을 만들지 않는다.
